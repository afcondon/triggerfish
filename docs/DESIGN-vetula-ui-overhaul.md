# Vetula UI overhaul (design)

Branch: `vetula-ui-overhaul`. The *concept* works well; the UI does not — poor
use of space, confusing controls, and the workflow falls apart once a
progression exists. This is a from-the-studs rethink of the surface, not a
tweak. Guiding steer (unchanged): compositional, gesture-first, theory hidden;
in the chord discs only the stave glyph + circle are fixed, every colour is a
free channel (see the feedback memories).

## The core reframing

Today Vetula tangles three concerns across two tabs (Lab = chord-building
lattice; Performance = voices + playback). Untangle them into **three
first-class objects** and almost every listed pain dissolves:

### 1. The SHAPE LIBRARY — a movable-shape vocabulary
Not a key-locked working pool (my earlier framing, dropped) but a **parallel
library of chord SHAPES** you build up and pull from, separate from the diatonic
lattice. Each entry is a chord stored as a *shape* plus the KEY it was saved in;
bringing one out **chromatically transposes** it into the current key — like a
guitar chord shape slid along the neck. No scale pertains: no diatonic/degree
transposition, just the movable shape. This is the concrete answer to "collect
chords independently of progressions," and because a shape is key-portable by
construction, a KEY change never disturbs it. Lives as a **small strip on the
LHS**. Naming / saving mechanics: TBD later.

**Systematised, not a flat bag.** The library organises into named GROUPS of
nice chords: the McMullen signposts fold in as one group, alongside others — an
added-tone / "mu" family (the close major-triad-plus-2nd Steely Dan fetishised,
really an impressionist added-tone sonority — add2/add6/add9-no-7, Debussy/Ravel
staples), quartal stacks, upper-structure triads, … — and the user's own saved
shapes are just another group.

**This is where colour earns its keep** (see below): show each library chord's
NEARNESS / AVAILABILITY to the progression in hand — how short a voice-leading
move it is from the current chord, and how much chromatic colour it adds against
the key. That's the bounded, shippable form of the planned force surface
(library chords as nodes, voice-leading motion as distance), computable with the
voice-leading engine Vetula already has (harmonia's `voiceLead` /
`enumerateVoicings`).

### 2. The PROGRESSION + the STACK — cheap, disposable, always captured
A progression is an ordered path through pool chords. Every progression
**auto-saves to a stack** with an autogenerated name/number; you later promote
the keepers. Consequences:
- The progression stops being the single fragile thing you fear to lose — it's
  cheap, so you break and backtrack freely.
- The stack is **also the undo history for KEY changes** (see below).
- Stack entries are **self-contained per key** — concrete voicings baked in, so
  a C-major snapshot stays C-major regardless of later key changes.
- **Stack → exploration is a round-trip (AC, 2026-07-04):** drag a stack entry
  back into the chord-exploration area to re-open and evolve it — its chords land
  on the lattice, revoiceable and branchable, and the auto-capture forks a fresh
  `◦`. This is the direct fix for "the workflow is bad once a progression
  exists": the stack is a *living source*, not a one-way archive. It also makes
  the Lab+Performance merge concrete — the drag *is* the seam between them.

### 3. The PLAYHEADS as Tidal — live-coded, not a form
**Decided: the per-voice durs/phase grid is replaced by a Tidal string.** The
playheads that read the progression into the odo / midi voices become Tidal
patterns. Editing a string beats editing a form, and a **commit button** (not
debounced autosave) lets one edit make a dramatic change across several voices
atomically. "Several interlocking chords arpeggiating on different patterns"
becomes natural. Lines up with #50 (Tidal drives Odonus).

- The live **jump** (nav strip, already shipped) stays a *runtime* re-anchor of
  where "now" reads into the evaluated pattern — it never rewrites the text, so
  it coexists with the commit-button edit model.
- Outputs are realistically few (odo; midi: block / arp / strum), but multiple
  interlocking midi patterns are the interesting frontier.

## KEY change = snapshot + transpose (non-destructive)

The one operation that resolves "don't lose everything on key change" and
"transpose a progression sometimes":

1. If the current progression is non-empty and changed since the last snapshot,
   **push it to the stack** (self-contained, in its current key).
2. **Transpose** the progression to the new key. (The shape library is
   key-portable by construction, so it's untouched.)

To the user the on-screen progression simply transposes; the pre-transpose
version is quietly preserved on the stack. "Make it in C, copy to G, tweak a
couple of voicings" is just: change key, then edit.

## The surface

Lab and Performance **re-unify** into one surface. Two chord SOURCES — the
diatonic **lattice** (find chords by theory) and the **shape-library strip** on
the LHS (your movable-shape vocabulary) — feed the **progression**, which the
**Tidal playheads** read. The lattice becomes a **zoom/drag** region that
expands only when you're hunting chords — killing the opening blank canvas.
(Deeper Lab-lattice ergonomics are explicitly *later*.)

## Colour — first concrete job found: nearness / availability

Colour is a free channel. Its **first real job has surfaced**: on the shape-
library strip, encode each chord's NEARNESS (minimal voice-leading motion from
the in-hand chord — harmonia's engine already computes it) and AVAILABILITY
(chromatic content against the current key). This is the bounded version of the
force surface (nodes = library chords, distance = voice-leading motion), and it
stops colour being decorative — it's a live "these are a half-step away, these
are a leap" readout while composing. Other candidate uses stay open (which
playhead is reading a chord; audition recency; note / chord identity) and get
decided as their structures land.

## Slice plan (each slice builds + rig-tests)

1. **Auto-save stack** — the library becomes a free capture stack (autonames +
   promote). Foundational; makes everything else non-destructive.
2. **Non-destructive KEY change** — snapshot + transpose, on top of (1). Kills
   the biggest workflow pain immediately.
3. **Playheads-as-Tidal** — replace the durs/phase grid with a Tidal source +
   commit button; evaluate to the per-voice schedule; jump stays a runtime
   re-anchor. The big one — do it once (1) makes experiments cheap.
4. **Unify Lab + Performance** into the pool → progression → playheads surface
   with zoom/drag. Layout follows the now-separated structure.
5. **Later** — the shape-library strip (movable-shape vocabulary), colour
   channel, Lab-lattice zoom ergonomics, and the ATLANTIS rig-jump (#77).

## Deferred / open

- ATLANTIS behaviour for the Tidal playheads (the rig runs the pushed brush; a
  pattern edit needs a re-push — same seam as #77).
- Shape-library mechanics: how a shape re-roots when brought out (to the tonic?
  to a chosen degree? placed by the user?), and naming / saving.
- Drag-back-to-explore semantics: does dropping a stack entry EXPLODE its chords
  onto the lattice as editable nodes (re-seat each by pcs → lattice position) or
  just re-arm the path? And how imported / off-lattice chords find a home.
- Colour (above), Lab-lattice zoom (above).

## Slice 3 — as built (playheads as Tidal)

Chose **true index-patterns** (not a durs re-encode) and **1 cycle = 1 bar = 16
pulses**. Architecture, seam-first:

- **The segment clock is the byte-identical seam.** `Reef.Vetula.Perf` already ran
  the realiser (block/arp/strum, cursor, strum-sustain) off a segment list
  `Array {ix,start,len}` — `durs` was only ever an *input to* `timeline`. Refactored
  reef to expose `PerfClock {segs, loopLen}` + clock-based cores (`cursorAtClock`,
  `renderClockMidiAt`); `cursorAt`/`renderVoiceMidiAt` are now thin `durs` wrappers
  (`clockOfDurs`). **All 14 reef goldens pass unchanged** — the durs path is proven
  behaviour-preserving.
- **`Vetula.Playhead`** (new, frontend) parses a mini-notation string via the vendored
  Tidal engine and QUERIES it over its period → the same segment clock. `clockFor`
  picks pattern-if-present else `durs`. A voice gained `pattern` (committed) +
  `patternDraft` (edit buffer); `stepVoice`/`cursorAt`/`jumpVoice`/nav-strip all read
  `voiceClock`. The live nav-jump still works: it re-anchors `phase` into the
  *evaluated* pattern, never rewriting text.
- **UI**: the durs matrix is gone. The chord table is now pure **Progression**
  (ladders + active-chord highlight); a new **Playheads** list gives each voice a
  mini-notation input + **commit** button (atomic, not debounced) + a status readout
  (parse error, or committed loop-length in bars, • when uncommitted).

**Mini-notation vocabulary (verified against this engine, `nChords=4`):**
- `"0 1 2 3"` = a chord per beat (all four in one bar). `"0(3,8)"` euclid, `~` rest,
  `[…]` groups, `*`/`!` all work. Out-of-range indices and non-numerics drop (= rests).
- **One chord per bar** = `"[0 1 2 3]/4"` (bracketed `/` slow → loopLen 64, one/bar).
  This is `defaultPattern n` and the empty-pattern fallback clock.
- **Gotcha**: this engine parses `<…>` as *grouping*, NOT slow-alternation — so
  `<0 1 2 3>` behaves like `0 1 2 3`, not one-per-bar. Use `[…]/n`. (`..` enum and
  `@` elongate are also flaky in the engine; noted, not blocking.) Sub-bar subdivisions
  that don't divide 16 (triplets) round to the nearest pulse — the rig IS a 16-grid.

**Deferred to #77 (ATLANTIS):** the rig still receives `durs` (unchanged wire); a
voice with a committed *pattern* diverges on push until reef learns to parse the
pattern on the BEAM. The segment clock is the seam, so that's a localized future
change (move `Vetula.Playhead`'s parse+query into reef), byte-identical by
construction. SOLO is complete and non-divergent.
